# Git access: implementation status and operator gates

## Current status

This is **not deployed protection**. The new `git-access.py` helper is not connected to the launchers. Existing launcher credentials, GitHub protections and running sandboxes are unchanged.

Implemented and tested locally:

- Read-only identity inspection against a private, host-owned registry: exact checkout/gitdir/common-dir paths, local-mirror edges, hostile config/includes/rewrites, linked worktrees and numeric GitHub repository identity.
- No-bypass `~ALL` history/deletion and default-branch PR floor evaluation, with active-rule corroboration and preservation of stronger requirements.
- Dedicated App inspector authentication, repository/permission-narrowed installation tokens, paginated reads, fixed-host/no-redirect transport, and secret-free denials.

Host-confirmed enrollment is now implemented: an explicitly approved App/repository mapping, matching local metadata, a complete fresh protection check and an exact confirmation phrase are required before an atomic owner-only registry update. Confirmation is followed by another fresh check, not reuse of earlier evidence. Concurrent registry changes abort rather than being overwritten. This code has only been fixture-tested for enrollment; no production registry is provisioned or enrolled.

Runtime role verification and quota accounting are now fixture-tested in the in-process admission/scheduled/write checks. The installed Greywall read-only/socket primitive and fail-closed launcher dependency check are verified below. Still unavailable: production credential/rate setup and acceptance, the session supervisor, broker writes, launcher-integrated read-only fallback and migration/rollout. A `verified` inspection or successful enrollment is **not** a sandbox lease or Git-write authorization.

The standalone `git-broker.py` wire parser is socketpair-tested for strict framed Git requests, duplicate/unknown fields, bounded private-file spooling, truncation/trailing-byte rejection and total/idle deadlines. Capability syntax is **not authentication or admission**. There is no listener, capability binding, credential lookup, upstream forwarding or launcher connection in this slice; direct CLI invocation fails with `broker_channel_unavailable` (exit 77). Broker task B1 remains incomplete until host binding, revocation and channel lifecycle are implemented and tested.

Runtime credential records are host-reviewed **attestations**, not permissions inferred from a successful API call. A repository's `credential_roles` references distinct `read` and `forward` IDs in the same registry's `runtime_credentials` list. Each profile binds `id`, `role`, `kind: fine_grained_pat`, the sole selected `repository_id`, GitHub `actor_id`, exact `permissions`, SHA-256 `fingerprint`, `key_epoch`, explicit `setup_approved`, and integer UTC `reviewed_at`, `valid_until`, `expires_at` values. Review validity cannot exceed token expiry. Keyring lookup is fixed to service `cockpit-github-runtime`, repository ID, credential ID and epoch; legacy `agent-gh` entries and agent environment tokens are never fallback sources.

The read profile requires the inventoried Metadata/Contents/Issues/Pull requests/Checks/Commit statuses/Actions grants, **all read-only**. Forwarding may write only Contents/Issues/Pull requests as reviewed; typed operation-specific checks remain a broker prerequisite. Administration/Workflows and Checks/Statuses/Actions write are refused. Profiles must use different fingerprints; both profiles are validated before either secret is read. Each non-inspection check verifies the actual keyring fingerprint, authenticated actor and numeric repository through read-only API requests, then rechecks review expiry and the unchanged registry/local identity before reporting role eligibility. The four runtime API probes are reported separately in `request_counts.runtime`; they are not free or hidden inside the seven-request protection estimate. No token is returned in a report or exported to an agent by this code.

PAT exact grants/repository selection require human review because GitHub does not provide complete programmatic PAT-grant introspection. Actor/repository GET success and an empty OAuth-scopes header **do not prove read-only permissions**. Nonempty classic scopes are rejected, but missing scopes never substitutes for the fingerprint-bound host attestation. Never copy fixture approvals, relabel an existing write token as read-only or widen an enrolled token's grants in place. Production setup, Checks compatibility and narrowly scoped read/write endpoint acceptance remain separately gated; no setup command or real credential was run here. The public `inspect` CLI deliberately remains protection-only and does not retrieve runtime tokens; its success is not admission.

### Shared quota ledger and inspector integration: no runtime rollout yet

`github-rate.py` is fixture-tested for principal/resource accounting at the fixed host-only path `~/.local/state/greywall-agents/github-rate.json`. It uses private owner-only files, an inter-process lock and atomic saves. Callers are trusted host code; no client may choose principal/bucket, path or purpose. Pools use `installation:ID:RESOURCE`, `user:ID:RESOURCE` or `app:ID:RESOURCE`, never token/repository/session IDs as independent allowances. REST, GraphQL, search and authentication resources stay distinct. No 5,000/hour allowance is assumed: missing, exhausted or expired server observations deny reservations. Actual mint-bucket assignment still needs observed setup evidence, not an assumption that every mint is free or has a separate quota.

Complete-check reservations charge all known pools atomically; failed reservations do not partially spend other pools. Extra pages/guards require credit before dispatch. Server headers reconcile downward without restoring capacity already reserved; Retry-After/403/429 and exhausted server quota also stop previously reserved dispatches. Reservations are bound to their observed reset window so old allocations cannot become free credit after reset. Unused/failed reservations are conservatively not refunded; this may reduce capacity but cannot create optimistic quota. Clock rollback and corrupt/untrusted state fail closed; a new boot invalidates old budget/evidence state.

**20% headroom policy approved by Theo:** automated admission, scheduled checks and writes must leave at least `ceil(observed_limit / 5)` in every involved primary pool. Both reservation and dispatch enforce it, including dynamically discovered pages and already-reserved requests after new server observations. Read-only inspection may consume this reserve, but that purpose cannot authorize an operation. Global upstream concurrency and content-mutation rates remain separately gated.

**Transport profile approved by Theo:** 16 KiB headers, 1 MiB JSON/receive-command prefixes, 1 GiB Git bodies, 1,024 updated refs, two requests/session, one upstream write/repository, 15-minute total transfer and 30-second idle deadlines. Only header/Git-body framing and deadlines are implemented in the reject-only parser so far; the remaining caps must be enforced in their respective future layers before service. No production role/rate setup, socket publication or write enablement follows from this approval.

Only scheduled checks may coalesce complete protection evidence per numeric repository and current evidence key, at most 300 monotonic seconds. Concurrent scheduled scans for one repository are excluded. Cached results return the **original** checked-at/expiry times: consumers must not re-age evidence or extend a lease using receipt time. Admissions/writes always reserve a new complete check; read snapshots never become merge evidence. This module neither verifies protections nor creates leases; only the trusted complete inspector may publish its narrow evidence projection after success. Local checkout checks must still run separately for every session.

The arithmetic tests retain all reviewed examples and installation/user splits (1,660; 3,080; 1,008; 3,412; 2,920 and historical 60-second comparisons). These are illustrative totals before actual mint and additional runtime-role probe overhead. Actual principal costs, pages, host/native readers and merge guards must be measured, not hidden in the seven-request protection estimate.

The in-process inspector now reserves before minting/inspection/runtime-role probes, charges each request before transport and reconciles actual response headers. The host App profile must explicitly approve `rate_setup_approved` and its `rate_buckets` installation/authentication mapping; installation inspection is tied to that exact installation's core bucket, while authentication must identify the observed approved App/installation resource. Runtime PAT probes share their actual actor's user/core pool. Resource mismatches, absent measurements or insufficient whole-check headroom deny before requests; no default quota or personal inspector fallback is introduced. Additional pages must acquire credit or the entire check fails, never succeeds on a truncated snapshot.

Only `purpose: scheduled` coalesces remote evidence against the unchanged registry/helper-policy digest; local checkout/gitdir/common-dir/config checks, profile expiry and keyring fingerprints still run for each caller. The returned checked-at time is the original ledger timestamp, not a fresh lease. Failed or late checks invalidate scheduled evidence; role-success/rate-success flags are published only after final checks.

Host-only `inspect_access(..., purpose='write', operation_costs=...)` requires explicit, trusted action pricing against the forwarding actor's observed pool. It reserves the complete inspection plus those operation costs, rechecks operation readiness against the latest headers after inspection, then returns a private `rate_reservation` handle. The future broker must charge that exact action before dispatch and finish the reservation; expiry/quota/headroom changes still deny then. Socket clients may never choose this purpose, pricing, principal or handle. Unknown action cost fails closed; a session lease or cached result never funds a write.

**Still not wired:** broker dispatch, session supervisor/coalescing, native/host command-level measurements and launcher enforcement. The public protection-only `inspect` CLI and explicit host admin remediation are not runtime write channels or quota-setup commands. Production must first obtain actual approved principal/resource measurements; tests seeded only synthetic quota data in scratch homes. No real host ledger, production credentials or write capability was created. Other concurrency/content-mutation limits remain unapproved.

Administrative preview is implemented in `git-protection.py`: `tools/agent-github.sh protect PROJECT` (also `make agent-github-protect PROJECT=...`) prints an identity-bound before/after mutation plan. It no longer executes the legacy name-based overwrite. Exit 0 with `mode: preview` means a plan was produced, not that protections were installed or verified. The project must already be in the host registry; preview cannot bootstrap enrollment or assign baseline ownership.

Plans create separate all-branch history and default-PR baselines, never adopt rules by name, preserve stronger owned rules/CI/review parameters and leave unrelated rulesets/classic protection untouched. Missing owned IDs, duplicate/colliding names, unknown bypass data or changed scope require operator review. Preview uses only the dedicated App inspection role; it performs no protection writes or registry updates and releases no credentials.

**Apply code is fixture-tested, not approved for production execution.** A separately approved host invocation may add `--apply` to `tools/agent-github.sh protect PROJECT`. It prints the full plan and requires the exact `APPLY OWNER/REPO NUMERIC_ID` phrase, then obtains fresh App evidence and aborts if the reviewed plan, registry or local identity changed. Each mutation has its own complete recheck and 30-second round deadline. Admin authentication is the host's existing `gh` login, not the inspector App or agent credential: fixed executable/config, agent `GH_*`/`GITHUB_*` variables stripped, credential captured only in host memory. It immediately rechecks numeric repository identity and uses fixed-host/no-redirect/no-retry HTTP for only the planned ruleset POST/PUT. No admin operation is available through inspection, launch or a broker route.

After each write the App independently reads back the requested fields, including preserved stronger rules, and final success requires the existing complete protection evaluator. Creation records only validated numeric IDs in the owner-only registry. Partial creation retains successful protections/IDs and remains read-only; there is no rollback, deletion, name-based adoption or automatic retry. Timeout, malformed response, lost response or failed post-check means **unknown/partial upstream outcome**: reconcile read-only before another reviewed attempt. This is not atomic with GitHub administrator changes.

**Initial bootstrap is fixture-tested too, not production-approved.** For an unregistered project, `protect PROJECT --bootstrap` requires all of `--checkout`, `--repository`, `--repository-id` and `--inspector-app-id`. Without `--apply`, it only previews and persists nothing. The App/owner/numeric repository mapping must already have separate host approval; bootstrap cannot create an App, broaden grants/repository selection, borrow another project's identity or replace an existing record. Local and App identity checks run before preview. Applying requires a phrase that also includes the exact checkout path, followed by fresh checks; checkout/gitdir/common-dir paths are part of the reviewed plan, not just config-content hashes.

Only after confirmation does bootstrap save the checked identity with **no baseline IDs**, then create and independently verify the two baselines. A prepared identity is not write admission: missing/partial baselines fail the same inspector. Failures preserve a read-only prepared record and successful IDs for reviewed recovery with ordinary `protect PROJECT`; no automatic weakening or duplicate creation. Existing `git-access.py enroll` retains its stricter contract of saving only after complete protection verification. Both paths share the same identity/App approval validator. Never provision host approval records by copying fixtures.

The legacy token-creation template no longer requests Workflows write; it retains Contents/Issues/Pull requests write and Actions/Commit statuses/Metadata read. This edits a future setup template, **not existing grants or their revocation**, and does not enroll a token for broker/native-read use. GitHub's [documented URL parameter table](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) lists `statuses` but not `checks`, and documents a fine-grained-token Checks limitation. No invented `checks=read`, broad classic scope or human-read fallback is added. The exact supported read role/Checks route must be proved before rollout; failure leaves it read-only/unavailable, not silently green CI.

## Safe local inspection

From the repository root, this reads local metadata and returns a JSON decision:

```sh
/usr/bin/python3 -I config/bin/.local/bin/greywall-agents/git-access.py inspect --checkout "$PWD"
```

Exit 1 means read-only/denied; exit 0 means the configured inspector verified identity/protections, **not** that broker/containment rollout gates passed. `--help` lists supported CLI commands. Without an enrolled record/App, inspection never consults your personal GitHub login or exports a credential.

The host admin script also exposes `inspect`/`enroll`; the Makefile has `agent-github-inspect CHECKOUT=...` and an explicit-ID `agent-github-enroll` target. These are host-run entry points, not launcher integration. Inspect denial propagates a nonzero make status while retaining JSON output. See `tools/agent-github.sh enroll --help` for the exact enrollment flags; all of checkout, project key, canonical repository, numeric repository/App IDs and both baseline IDs must be supplied, not derived from a basename or mutable remote.

Do not populate a real registry by copying test fixture approvals. The registry location is fixed under `~/.config/greywall-agents/git-repositories.json`, with owner-only permissions; no command-line/environment registry override is accepted. Registry and keyring access must stay outside sandbox mounts when launcher integration is implemented.

Registry version 1 has `repositories` plus a host-reviewed `inspector_apps` list. Each App entry binds App/client/installation/owner IDs, `owner_login`, `approved_repository_ids`, key epoch, exact permission map and explicit setup approval; Administration write requires its own explicit approval flag. Repository records reference App/installation IDs, **not copied approval flags**: every inspection resolves the current global profile, so revoking setup/repository approval blocks existing enrollments even with a cached auth token. The operator must approve actual installation access and IDs before this profile exists. Enrollment preserves other records; it cannot provision an App, broaden repository access, grant permissions or reassign a project to another repository. Profiles hold references/approval metadata, never keys or tokens.

- Run the full test suite and obtain independent security review before deployment. The author's self-review is not independent certification.
- Prove real Greywall recursive read-only project/metadata mounts and per-session socket isolation. Metadata pinning alone permits index/ref updates and is not that proof. No PATH shim or missing token substitutes for filesystem enforcement.
- Finish broker/supervisor/native-read accounting on the implemented shared ledger and measure actual production principal/resource headroom. Inspection requests share their App installation bucket, forwarding/read PATs share the appropriate user pool, and App-token mint overhead is counted separately. - Keep approved timing: 300-second scheduled checks, 600-second hard local admission ceiling, 30-second complete inspection deadline; **each mutative upstream request gets its own fresh inspection**. First failed scheduled check contains immediately, not at expiry. Suspend/resume and supervisor death invalidate/contain as specified.
- Preserve necessary GitHub reads/issues/comments/reviews/PRs/Projects and authorized merges. No generic authenticated mutation tunnel, bypass, review dismissal, forged check/status, weaker CI or raw write-token fallback.
- Review each affected CI job's append-only/new-branch replacement and retained protected branches. Keep job purpose, required checks and repeated-run/deployment behavior; do not disable jobs silently. Stack/fork/queue compatibility must be proven before affected cutover.
- Inventory active/sleeping sessions, clones/worktrees/common directories, submodules, external writers and previously exposed tokens. Revoke legacy credentials on GitHub and confirm the result; deleting a local secret or restarting a session is not revocation. Quarantine out-of-process Docker/automation writers without destroying working trees.

Rollback is enforced read-only, never unconditional credential export or removal of stronger GitHub protections. An interrupted/forwarded write may have completed remotely; reconcile using read-only data rather than replaying it or claiming it was rolled back.
