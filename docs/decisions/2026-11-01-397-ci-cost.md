# CI spends its minutes where the measurements put them; no merge queue

Issue #397. Theo asked for this scope on 2026-11-01, naming rust-cache per job among the
caches to add; the worker chose each change from the measurements below. Two revisited sections follow: the
build-cache rules of #127 (the WSL 2 job stays uncached) and Theo's reversal on draft pull
requests.

Measured on the 183 CI runs with today's job set (2026-10-31 00:57 to 2026-11-01 15:42 UTC,
every run since the legacy job left) and the 71 pull requests merged in that window, with
`gh run list` and `gh api repos/Androlax2/agent-cockpit/actions/runs/<id>/jobs`. Billed
minutes round each job up to the minute, macOS ×10 and Windows ×2. The repository is public,
so GitHub bills none of them; they still measure runner time and the five-job macOS limit.

| Per merged pull request | Pull request runs | `main` run | Total |
| --- | --- | --- | --- |
| Runs | 1.51 (27 of 71 had more than one) | 1 | |
| Runner minutes | 21.7 | 11.5 | 33.2 |
| Billed-equivalent minutes | 64.2 | 35.8 | 100 |

| Job (billed-equivalent minutes, both events) | Minutes | Typical run |
| --- | --- | --- |
| `greenfield-macos` | 3970 | 1.5–2.5 min, cache restored on 29 of 29 sampled runs |
| `greenfield-wsl2` | 1586 | 4–5 min: `setup-wsl` 1.3, uncached build and tests 3 |
| `greenfield` | 836 | 5–7 min, uncached; last to finish in 69 of 126 green runs |
| `docs` | 653 | 3–4 min, of which `cargo install lychee` 2.5–3.5 |

A green run takes 5.1 minutes from start to last job (p90 6.8); jobs wait about 3 s for a
runner, so the platform jobs never delay a merge. A pull request merges 8.5 minutes after it
opens (median; p75 17, p90 34).

- **`docs` installs lychee's release binary, checksum verified, instead of compiling it.**
  About 3 minutes off every docs run, which also takes `docs` off the critical path. It no
  longer needs a Rust toolchain.
- **`greenfield` restores the same pinned `Swatinem/rust-cache` as `greenfield-macos`, saved
  only on `main`** (the rules of the #127 section below). It is the job every
  merge waits for, so its build time is the merge time. The caches use 7.3 of the repository's
  10 GB, nearly all of it stale macOS entries (0.55 GB each); GitHub evicts the least recently
  used first, and the entries in use are read on every run.
- **The macOS and WSL 2 jobs run on a pull request only when it changes a crate they build**
  (`tools/ci-jobs.py`): the crates they test or whose programs their tests start
  (`PLATFORM_ROOTS`) and every crate those depend on, read from the manifests, plus the root
  manifests and `ci.yml`. No dependency of the daemon reaches `main` without its platform run,
  the rule #127 set. That leaves `cockpit-workspace-rules`, the Makefile and other workflow
  files: run on the 93 merged pull requests' files, this skips the platform jobs for 3 of the
  86 that reach the greenfield job. Small, but it costs no proof. A skipped job reports
  success, so the ruleset's five required checks stay as they are.
- **`prerelease.yml` parses again.** A colon followed by a space inside a plain `run:` scalar made GitHub reject the
  file, record a failed run on every push (141 so far) and offer no dispatch.
  `tools/tests/test_workflow_syntax.py` guards every workflow.
- **No merge queue.** GitHub offers it only on repositories owned by an organization; this one
  is owned by a user. It would also add a `merge_group` run per pull request to today's 1.51,
  while `main` already merges without requiring an up-to-date branch: a pull request is rebased
  only on a real conflict. Auto-merge plus a rebase on conflict stays the flow.
- **Rejected: no CI on draft pull requests.** No pull request in this repository was ever a
  draft; skipping would save nothing and leave a skipped-means-green window at
  `ready_for_review`. Theo reversed this on 2026-11-02 (the draft section below).
- **Rejected: platform jobs only for crates with OS-specific code, `main` as the backstop.**
  `main` runs cancel each other and nobody is alerted when one fails, so a break would surface
  on an unrelated pull request.
- **Rejected: selecting `main` pushes by their diff.** `main` runs cancel each other (24 of 72);
  a docs-only merge cancelling the run of the crate merge before it would leave that change
  unproven on every platform.
- **Unchanged:** WSL 2 stays uncached (the #127 section below); the release
  workflow, which already builds on pull requests only for its own machinery.
- **Open (`validate`):** the gain of each change, and the acceptance's before/after table over
  15 merged pull requests, are measured after this merges and recorded on #397.

Regression tests: `tools/tests/test_ci_jobs.py`, `tools/tests/test_ci_bootstrap.py`,
`tools/tests/test_workflow_syntax.py`.

## Revisited 2026-10-31 (#127, the build cache)

Decided by Theo for the cache action (he pre-approved one pinned `Swatinem/rust-cache` on the
macOS job) and by the worker for the rest, from the job durations of five green `main` runs
(41209922817 to 41215764505): `greenfield-macos` took 112 to 214 s, of which the toolchain and
installer, about 15 s, are not cacheable and the build and tests were 97 to 193 s; `greenfield-wsl2` took 169 to 228 s, of which `setup-wsl` was 66 to
86 s and the build and tests 84 to 120 s. The cache rules now govern the `greenfield` job on
Linux too (the #397 bullet above).

- **`Swatinem/rust-cache`, pinned to v2.9.3's commit.** It caches the registry and the
  dependencies' build output, not the workspace crates. Its key adds a hash of the manifests
  and `Cargo.lock` to the toolchain and job; a lockfile change misses the key, restores the
  newest entry for the same toolchain and job, and rebuilds only what changed.
- **Only `main` saves (`save-if`).** Pull requests restore from the base branch. `main` saves
  a new entry only when the key changes (an exact hit skips the save), which is when the
  cached dependencies change; a `main` run cancelled by the next merge saves nothing and the
  next completed run does. Saving per pull request would fill the repository's 10 GB cache
  quota with entries no other branch can read.
- **`cache-bin: false`.** `~/.cargo/bin` holds the cargo-nextest that `install-action` just
  installed against a reviewed hash; restoring a cached copy over it would make the cache, not
  the pin, decide which binary runs.
- **WSL2 stays uncached.** `actions/cache` runs on the Windows host and cannot see the
  distribution's file system: a cache means tarring the registry and `target/` across DrvFs
  in both directions on every run, plus a second new action. The build it could save is
  84–120 s, a little over half the job, and the copy through DrvFs would eat into that; the
  largest fixed cost, `setup-wsl`, is not cacheable at all.
- **`rust-toolchain.toml`'s clippy and rustfmt stay.** Both platform jobs download them on
  the first cargo call for nothing (10–30 s), but overriding the file would state the
  toolchain version twice; the issue ties that change to the WSL cache, which that job does
  not get.
- **Rejected:** running the platform jobs only on `main` and on `crates/cockpit-daemon/**`
  changes. A change to any crate the daemon depends on would then reach `main` untested on
  macOS and WSL2, which the M0 gate (#27) exists to prevent.
- **Open (`validate`):** the macOS saving is measured on the second `main` run after #127
  merged, the first one that can restore a saved cache; the result is recorded on #127.

Regression test: `tools/tests/test_ci_bootstrap.py`
(`test_cached_jobs_restore_the_pinned_rust_cache_saved_only_on_main`, which covers the Linux
job too since #397).

## Revisited 2026-11-02 (#397, draft pull requests)

Theo's direct decision on 2026-11-02 reverses the rejection of draft skipping above. This is
bounded #397 follow-through; the merged #531 baseline and measured-savings acceptance are
separate. Draft pull requests do not execute workflow jobs.

- **All four PR-triggered workflows subscribe to `opened`, `synchronize`, `reopened` and
  `ready_for_review`.** Their PR-capable jobs reject `github.event.pull_request.draft` before
  runner allocation, including matrix expansion. Generated draft release proposals have no
  exception. Existing non-PR-only jobs and tag-only release gates remain intact; downstream
  jobs retain their default successful-dependency requirement.
- **Everything else keeps its conditions:** main pushes, release tags, schedules, manual
  dispatches and docs publication events; PR path filters and the five required CI context
  names are unchanged. GitHub can still create skipped run/check records; drafts do not
  disappear from Actions history, and a run already started before conversion to draft is not
  cancelled.
- **Drafts cannot merge.** After marking ready, wait for the automatically triggered checks
  on the exact head to execute and pass; skipped draft results never establish tested code
  or authorize a merge. No required-check settings or repository protections change.

Evidence: `tools/tests/test_workflow_drafts.py` exercises the actual job expressions with
draft, ready and non-PR contexts, checks the readiness subscription, and preserves selection
and publication restrictions. Hosted draft/ready verification establishes GitHub's actual
execution behavior; local expression tests do not implement the Actions scheduler.
