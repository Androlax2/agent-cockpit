# Revalidate Codex 0.166.0 before promoting its capability pin

Issue #436. Decided by Theo: Option B, move to 0.166.0 after revalidation.

- **Pin only measured capabilities.** Native 0.166.0 checks cover Resume, Events,
  Submit, Cancel and Outcome using the real adapter, launcher, app-server and TUI
  with local canned model responses. Older, different and unknown versions remain
  unverified. No new capability is advertised.
- **Isolate the native suite.** Cleared child environments and scratch homes replace
  placeholder-key requests to real endpoints. Helpers have deadlines and output
  bounds; private process groups and tmux are cleaned up. Effective configuration
  is checked before native turns.
- **Default keymaps are not overrides.** A resumed 0.166.0 scratch home reports
  object/null default binding slots. Accept those; refuse all concrete values and
  arrays, including empty unbindings. Ordinary regressions and native refusal tests
  cover the distinction before automated Escape cancellation is used.
- **Preserve provenance.** Historical 0.161.0 captures remain labelled 0.161.0.
  The six upstream input schemas are byte-identical on 0.166.0; reuse them rather
  than copying and relabelling payloads. Exact blobs, executable identity and
  failed/successful receipts are in the
  [evidence record](../../crates/cockpit-codex/tests/fixtures/codex-0.166.0/README.md).
- **Acceptance stays separate.** Signed-in approval routing (#436), daemon-launched
  instruction recognition (#419), WSL2 acceptance and releases still need their
  own evidence and approvals. A refused historical live attempt is not a pass.
- **Rejected:** advancing the version label on fixture replay alone, routing
  placeholder keys to a real endpoint, or bypassing owner configuration guards.
