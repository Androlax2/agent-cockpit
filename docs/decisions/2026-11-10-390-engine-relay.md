# Forwards reach a project's engine through a relay in its network namespace

Status: accepted

Issue #390, part 2 (the `containers` service of #860). Decided by Theo through the
coordinator, answering the worker's proposals.

- **The engine keeps `PrivateNetwork=yes`; a relay joins its namespace** (B). The
  `torlek-engine-relay@` unit runs as the engine user with `JoinsNamespaceOf=` the engine's
  unit, so `127.0.0.1` there holds only that engine's published ports: another project's
  engine is out of reach by construction, not by a check. It listens on
  `/run/<user>/relay.sock`, which only the owner's uid reaches (folder ACL) and is served
  (`SO_PEERCRED`); a line names the port (`crates/cockpit-sandbox-launcher/src/engine_relay.rs`).
  The relay trusts every process of the owner's uid, so the per-port approval is the
  launcher's to enforce: a session must never be given the socket or its folder.
- **The relay is the owner's installed `torlek-sandbox`, bound read-only into the unit** (A),
  not a root-owned copy: an upgrade applies when the engine restarts, with no setup to rerun.
  The cost: whatever can write the owner's Torlek install runs as that project's engine user.
- **Ports open live, each after an owner approval** (C): no list of ports in `config.toml`.
  The agent asks with an explicit command, as `torlek ask service` does; the launcher never
  files the request itself.
- **Rejected:** dropping `PrivateNetwork=` (the engine's own processes would reach the host's
  loopback services), a unit per port (only root adds units, so no port could open live),
  and a `socat` script (one more host dependency, and no test through the real entry point).
