# The greenfield tests are built once and the shards unpack that build

Status: accepted

Issue #1261. Theo asked for it on 2026-11-09; the worker chose the layout from the runs
cited in the pull request.

- **`greenfield-build` runs `cargo nextest archive` once; the test shards and
  `greenfield-sandbox` unpack the artifact and compile nothing.** Before, every shard and the
  sandbox job compiled the whole workspace (250 to 360 s each). The archive is about 2.4 GB
  (the test binaries statically link the database engine), so it travels uncompressed-twice:
  the artifact is uploaded with `compression-level: 0`. This reverses the rejection in
  `2026-11-06-997-sharded-greenfield-tests.md`, which estimated the transfer as costing more
  than the repeated builds; the pull request has the measured numbers.
- **Shards are cut by measured time, not by hash.** `tools/ci-shards.py` assigns the archive's
  test binaries, longest first, to the lightest shard, from `tools/ci-test-weights.json`
  (seconds per binary, refreshed from the shards' `junit-shard-N` artifacts). The plan is made
  from the archive's own list, so every binary runs in exactly one shard even when the weights
  file is stale or lacks a new binary; a stale file only unbalances the shards.
- **The programs tests start are in the archive, and the harnesses do not build.** The CLI and
  TUI end-to-end harnesses ran `cargo build` to find their programs; under
  `COCKPIT_PREBUILT_PROGRAMS` (set by `make crates-test-from-archive`) they fail on a missing
  program instead of compiling the workspace again. The archive carries the example daemon
  through `.config/nextest.toml`.
- **The required check is still `greenfield`;** it now also needs `greenfield-build`. No
  ruleset change, no check dropped or weakened.
- **Rejected:** a hash partition per shard (it cannot balance by time); sharing the archive
  with `greenfield-wsl2` in this change (a separate part: the distribution needs the
  workspace at the build's absolute path).
