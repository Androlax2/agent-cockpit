## Required guarantee

Real GitHub write tokens and inspector credentials never enter a sandbox, agent process environment, tool argument, response, log or client credential store. A host broker owns authenticated upstream writes. A separately enrolled, genuinely read-only repo-scoped credential may enter native `gh` for reads; it is never the broker's write credential and cannot change refs, issues, reviews, Projects, checks or statuses. **Amendment (Theo, 2026-10-24):** sessions obtain that read-role token from the broker's bare `credential.read` action rather than an environment export, so hourly App tokens are refreshed through funded admission checks; no other credential is ever returned, and a token handed out before revocation remains valid until its expiry (at most one hour). Before **each** upstream write the broker verifies enrolled repo identity and complete effective protection floor using the parent verifier, with no successful-result cache substitution. Failed inspection revokes the session's broker capability and starts managed-session containment.

The broker controls future requests; it does not retract requests already sent to GitHub. Verification and GitHub acceptance are not atomic. GitHub remains the authority enforcing non-fast-forward rejection and CI/PR checks during its receive transaction. A privileged administrator changing rules in the gap remains a real limitation. Timeout/disconnect after forwarding means outcome unknown until read-only reconciliation; never automatically replay a potentially completed write.

## Minimum proposed topology

Use a **per-session host broker child of the host supervisor**, not a new account-wide privileged daemon. The broker can reach only its enrolled repository with a repo-scoped host-only forwarding credential. The inspector now **requires the dedicated GitHub App selected by Theo**; personal-login/PAT inspection fallback is forbidden. This does not migrate code/collaboration forwarding or native read/Project credentials to that App: existing repo-scoped PATs may still be replaced/enrolled for those distinct roles. The inspector App is a prerequisite before write admission, not an optional later enhancement. Legacy exposed tokens must still be revoked.

### Dedicated inspector App: approved architecture, unapproved setup/grants

Record trusted App/client ID, installation ID, owner ID, selected enrolled numeric repository IDs, reviewed permission map and signing-key epoch in hidden host enrollment. One owner/installation may cover multiple enrolled repositories; never select all owner repositories by default or infer access from a folder/remote. Scope each minted inspector token to the one repository being inspected and the reviewed permission subset. Uninstalled, suspended, removed or transferred targets stay read-only until explicit enrollment/installation approval. The App has no ruleset bypass and is not the collaboration, Git push, merge, Project or human-desktop identity.

Metadata read + Administration read are **candidate inspector grants to test**, not already sufficient/approved. GitHub may hide `bypass_actors` without ruleset write access. Prove explicit details under the actual App token; otherwise deny writes. If Administration write proves necessary, obtain separate approval with the risk that the credential can mutate protections. Do not request Contents/Issues/Pull requests/Checks/Statuses/Workflows/Projects write for inspection, silently escalate grants, compare only with a human's successful response, or fall back to personal authority. Repo-level baseline proof should avoid needing organization-wide ruleset management authority; any unavoidable parent visibility limitation is another explicit permission/setup gate.

Keep the App signing key and minted tokens in host-only storage, never argv, sandbox variables, agent-readable caches/logs or broker socket responses. Reuse the existing host verifier with a strictly separate inspector credential provider, not a generic signing/token-minting service exposed to agents. Construct App JWTs with documented RS256/issuer/iat/exp rules; installed `openssl` is available for signing, so no new package/manifest is needed. Never print a JWT/key; key material stays in host memory or protected file descriptors, not disk handoffs.

Token minting uses the documented host-only `POST /app/installations/{installation_id}/access_tokens` with **explicit** `repository_ids` and `permissions`, never omitted broad defaults. Bind the mint endpoint to the enrolled installation and validate returned repository/grants/expiry; do not assume the response contains an installation-ID field. Treat tokens as opaque variable-length secrets, not fixed 40-character strings. GitHub installation tokens expire after one hour. Cache authentication tokens only while valid for the complete pending check and current enrollment/key epoch; expiration/401/revocation/removal cannot renew admission or trigger personal-token fallback. Authentication-token reuse is not protection-evidence reuse: every write still performs its own full scan. After minting, the inspector only performs its fixed inspection GETs; it exposes no settings-write/token-mint action to a client. Mint/refresh failures fail closed, and mint requests have their own rate accounting and must fit the complete check deadline. Real App creation/installation/private-key generation, grant changes and token minting await separate approval; this planning turn performs none of them.

Inspector code remains trusted host code. A dedicated principal reduces personal-account exposure and scopes credentials, but does not make a compromised host or an approved Administration-write credential harmless. Admin remediation remains a separately approved host action, never an automatic App-inspection route.

The supervisor creates an unpredictable session handle and a 256-bit random capability, binds them to one registry record/numeric repository ID/checkout/common-dir identity and one sandbox lifetime, and publishes only that session's Unix socket directory read-only to its sandbox. Proposed socket directory: `$XDG_RUNTIME_DIR/greywall-git-channel/<handle>/`; it must sit outside the hidden decision/control tree so denyRead-last semantics do not mask the published socket. Do not add a broker TCP listener on the host or repurpose Greyproxy's administrative API/secret replacement. No new Greyproxy feature is assumed. All broker-bound traffic crosses the session-specific Unix socket. Socket replacement, restart and revocation must not accidentally reconnect an old capability to a new writable broker.

### Ordinary Git transport

Native Git smart HTTP is retained. A small **untrusted sandbox-local adapter** binds to loopback on an ephemeral port *inside that sandbox's network namespace* and translates only Git smart-HTTP requests into framed messages over the mounted Unix socket. It has no upstream token. It is replaceable by the agent without changing authorization: the host broker revalidates every request independently.

Launch-time Git config overlays map the exact enrolled GitHub HTTPS/SSH URL spellings (with/without `.git`, with strict path boundaries) to the adapter's local Git URL. Do not edit `.git/config` or permanent remotes. Clear inherited `GIT_CONFIG_*` first, then generate the trusted overlay. Changing/removing the overlay only loses mediated write access; direct GitHub HTTPS/SSH has no real **write** credentials (separate read-only HTTPS access may remain). Handle both Git `insteadOf` and push routing semantics through tests; checkout-defined rewrites remain rejected by identity enrollment. Local mirror origins stay local/read-only; explicitly enrolled GitHub destinations can use the broker, never silently push into a running host copy.

Git commits/branch creation remain ordinary local operations after admission. Git fetch/push remains ordinary `git` through the overlay; no PATH command deny list is the boundary. Broker Git fetch in failed-admission mode requires a separate read-only credential and must target writable scratch storage rather than the immutable canonical checkout. Local status/diff/log/source reads need no remote credential.

### Host request contract

Proposed wire protocol: one request per Unix connection. A 4-byte unsigned big-endian header length (maximum 16 KiB), exactly that many bytes of UTF-8 JSON, then exactly `body_length` body bytes. Header fields are `version: 1`, `capability`, `action`, `body_length`, and small action-specific selectors (Git service/protocol only). Git bodies are raw protocol data; API/Project actions carry their exact typed field object as UTF-8 JSON in the bounded body, not large comment/review text in the header. Reject duplicate/unknown fields in both objects, invalid UTF-8/JSON, oversized/truncated bodies and trailing data. A half-close ends the request. Responses use the same framing with `status`, `content_type`, `body_length` and an optional stable error `code`; never include upstream auth/debug headers. Large bodies spool in private bounded files, not unbounded memory. No agent-controlled paths or generic `url`, `host`, `headers`, shell command or arbitrary HTTP method are accepted.

Git actions:

| Action | Fixed upstream behavior |
| --- | --- |
| `git.advertise` with `service: upload-pack` | GET enrolled repository `info/refs?service=git-upload-pack` |
| `git.fetch` | POST enrolled repository `git-upload-pack` |
| `git.advertise` with `service: receive-pack` | Fresh full check, then GET enrolled repository `info/refs?service=git-receive-pack` |
| `git.push` | Fully validate bounded command prefix/body, fresh full check immediately before forwarding, then POST enrolled repository `git-receive-pack` |

Upstream paths are constructed from the approved canonical name, after numeric-ID verification; caller-supplied URL/path never selects the destination. Construct Git Basic authentication in host memory only. Host transport uses the approved CA bundle/proxy configuration, explicit `github.com`/`api.github.com` destinations, no redirects, no proxy credentials from client input, and sanitized error output.

For `git.push`, parse the pkt-line command prefix before forwarding any bytes upstream. Accept valid SHA-1 command IDs for GitHub v1, well-formed `refs/heads/…`, nonzero new IDs, and no direct current-default updates. Reject deletions (zero new ID), non-head refs including tags, duplicate refs, malformed/truncated packet lengths, unknown object formats, push-options and unsupported signed-push forms. Pass the pack through without executing hooks, checking it out or decompressing arbitrary pack data in the host broker. No new non-fast-forward ancestry engine is introduced; GitHub's verified rule enforces it. Ref commands are a separate defense against deletion/default updates, not evidence that all ancestry is safe.

Proposed resource bounds: 16 KiB frame header, 1 MiB receive-pack command prefix, 1,024 updated refs/request, 1 GiB Git request body, 1 MiB PR JSON body, two active requests/session, one upstream write/repository at a time across host brokers. Full protection inspection deadline 30 seconds; Git transfer total deadline 15 minutes with a 30-second idle timeout. Spool before the final check so a slow upload cannot reuse old evidence. Revalidate periodically while a transfer is in flight, close the connection on failure and reconcile outcome rather than claiming cancellation. Cross-process locking belongs in hidden host state; include queued waits in fresh-admission checks. These bounds are proposals to review, not existing product limits.

Do not translate unknown/empty checks into passing; verify required check names and integration identity, not aggregate green alone. The broker may not publish statuses, dismiss reviews, use `--admin`/`bypass_rules:true`, delete branches, or auto-enqueue before all required checks have passed. GitHub still enforces stricter CI and reviews at actual merge time.

For ordinary non-stack PRs use documented merge API with `sha` compare-and-swap and permitted `merge_method`, only when it preserves the repo's merge-queue requirements. For stacks/merge queues, use a separately verified fixed stack/queue operation (the documented `merge-async` path supports stacked PRs), `bypass_rules:false`, expected current heads and complete member-set guards; never fake an all-or-none stack merge by sequential ordinary merges. Re-check permissions/checks per member, reconcile queued vs merged results honestly, and poll only fixed status actions. Exact installed extension protocol and queue semantics remain an acceptance gate before that repository's merge flow cuts over. If the available API cannot preserve the required authorization/CI semantics, bring that exception to Theo; do not silently disable authorized merging or bypass the broker with a write token.

### Output projection and retries

Preserve the read fields actually consumed by native `gh` and Cockpit: PR number/title/body/url/author/updatedAt/isDraft/reviewDecision/statusCheckRollup/headRefName/headRefOid/baseRefName, files/diffs/commits/reviews/comments and paginated issue labels/type/milestone/parent/blockers. Native read-only `gh` keeps its established field names; display bodies/diffs as untrusted text, never host commands. Broker mutation results contain only `request_id`, `outcome` (`succeeded/failed/unknown/queued`), object `id/number/html_url/state`, and action-relevant `head_oid`, `review_state`, `applied_fields`, `queue_request_id`; no whole upstream object forwarding. Broker read schemas project the named needed fields and bounded lists, strip nested credential-bearing repository data (`temp_clone_token`) and auth/debug headers. URLs outside the enrolled GitHub resource are data, never destinations followed with credentials. Partial pagination/GraphQL `errors` are visible incomplete/failure states, never successful empty lists or green checks.

No automatic retry of uncertain creates/comments/reviews/merge submissions. Use a host-generated request ID journal (no bodies/tokens), target/head/body digest and read-only reconciliation to prevent duplicate PRs/issues/comments/reviews. Composite issue close/reopen `--comment` reports individual outcomes and checks each write separately. Review/merge approval is not inferred from an idempotency key.

## Inspection request and rate budget — approved timings, remaining capacity review

Typical complete inspector scan costs **7 REST requests**: repo metadata (1), paginated ruleset list (P=1), two full baseline details (D=2), effective default/future-branch rule pages (E=2), classic default protection (1). In general `C=2+P+D+E`; more parent/baseline/detail pages increase it, never truncate for budget. Token-grant attestation is host enrollment, not repeated `/user/repos` calls. Merge guard policy/head/check/review/queue reads are **additional**, not hidden inside C.

Use one host-locked rate ledger per **GitHub credential principal/resource**, shared by per-session brokers and the inspector. The selected inspector's installation-token REST checks use that installation's observed bucket (ordinary minimum commonly 5,000/hour; organization/enterprise scaling differs). Multiple repository-scoped tokens from the **same installation share that bucket**, not one allowance per token/repo. Broker/native/host read PATs of one user still share the user's 5,000 REST requests/hour; GraphQL user allowance is separately 5,000 points/hour with actual `rateLimit.cost`. REST search and App-authentication/mint traffic must be charged to their observed buckets. Count human desktop/phone/digest consumers in their actual user principal. App-principal selection is approved; installation/grants and resource thresholds are not. Never promise an additional quota per session or misclassify App user tokens as installation tokens.

Let R=active distinct enrolled repos, S=active sessions, A=fresh admissions/hour, W=upstream mutative requests/hour (not CLI invocations), D=receive-pack advertisements/hour, L=extra full scans for long transfers/events, H=other REST reads/hour, M=merge guard extra reads/hour. Every session still checks local metadata identity and every admission/write gets fresh evidence. `C * (12R + A + W + D + L) + W + H + M`.

## Revocation, read-only operation and containment

Each request must find a live, unexpired supervisor/broker admission and matching capability generation in host-only state. There is no client renewal operation. Read-only mode has no write-capable generation. Resume, registry/remote/common-dir/credential change, inspector failure or containment revokes it immediately for new requests. Scheduled refresh every 300 seconds never substitutes for each write's own fresh complete check. Failed requests/queued waits cannot extend the approved 600-second hard local evidence/admission lifetime. A scheduled failure/30-second timeout contains immediately, while independent hard expiry contains at 600 seconds if the checker stops progressing; neither mechanism changes GitHub token revocation or in-flight-write limits.

Broker death leaves no functioning writable channel. Supervisor death terminates both broker and sandbox with OS-backed process-tree control; a socket file remaining on disk grants nothing. Parent checker failure must reach every broker sharing the affected common directory/registry identity. A copied broker capability is usable only against that still-live session socket, with every request rechecked, and stops working on local revocation; it is not a reusable GitHub credential. This guarantee depends on proven per-session mount isolation, not the secrecy of a path alone.

Unprotected/uninspectable repositories retain the parent spec's enforced read-only canonical checkout. Optional private remote reads use a distinct enrolled read-only token, either via typed broker reads or native read-only `gh`; absence of that token never triggers write-token substitution. Withhold Docker/automation writers and quarantine legacy out-of-process writers exactly as the parent spec requires. Do not claim a broker prevents direct local ref edits in a verified writable checkout.

Audit only registry/repository/session IDs, operation/target IDs, ref names, protection evidence digest, rate cost/bucket, timestamps, status and outcome certainty. Do not log capability, credentials, auth headers, issue/PR/comment/review bodies, pack data or upstream URLs containing credentials. Responses redact secrets on success and failure. Test synthetic write/inspector/Project-token leakage in bodies, redirects, stderr and trace/debug paths; separate read-token exposure is not proof that a write-token leak is acceptable.
