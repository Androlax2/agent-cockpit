## Approved intent and scope

Every repository used by an agent through Agent Cockpit, existing or future, must pass trusted identity and effective GitHub protection checks before receiving broker-mediated write access. Real GitHub write credentials remain outside agents in every mode. This is not an account-wide campaign against unrelated GitHub repositories. The four previously inspected repositories are samples, not an allowlist or the scope boundary.

Missing, disabled, bypassable, uninspectable or unsupported protections, malformed API responses, incomplete pagination, permission failures, network failures and timeouts mean read-only access, not optimistic write access. Agent instructions, hooks and command deny lists are not security boundaries.

Protect every existing and future branch against non-fast-forward history replacement and deletion. Require PRs on the default branch, with zero mandatory reviewers in the new baseline. Preserve existing CI requirements, reviews and stronger protections. Normal new feature branches and append-only commits/pushes remain usable after verification, subject to existing repository policy and the user's Git authorization.

This stage protects remote branch history and gates local project writes when checks fail. It does **not** prevent local reset, rebase, amend, direct ref edits or object deletion inside an admitted writable checkout. A complete local append-only Git gateway is a separate stage. Do not market this stage as universal local history protection. Tags are not part of the new all-branch baseline; preserve existing tag protections.

## Effective GitHub protection contract

Install two additive, repository-level branch rulesets after separate approval:

| Baseline | Target | Rules | Bypass |
| --- | --- | --- | --- |
| `agents: preserve all branch history` | include `["~ALL"]`, exclude `[]` | `non_fast_forward`, `deletion` | explicit `[]` |
| `agents: require default branch PR` | include `["~DEFAULT_BRANCH"]`, exclude `[]` | `pull_request` | explicit `[]` |

Both use `target: "branch"`, `enforcement: "active"`. Do not introduce `creation`, `update`, linear-history or all-branch PR restrictions. PR parameters initially match the existing zero-review policy: `required_approving_review_count: 0`, `dismiss_stale_reviews_on_push: false`, `require_code_owner_review: false`, `require_last_push_approval: false`, `required_review_thread_resolution: false`. This new floor does not lower stronger pre-existing requirements. Branch deletion restrictions also affect automatic post-merge cleanup and branch renaming; do not add a bypass to make cleanup work.

A **dedicated GitHub App inspector**, selected by Theo, must see full baseline details including `bypass_actors`; its signing key/JWT/installation tokens never enter a sandbox or serve broker forwarding requests. Install on selected enrolled Cockpit repositories only, bind App/installation/owner/numeric repository IDs in host enrollment, and never fall back to Theo's personal login/PAT for inspection. Future repositories require explicit enrollment and approved installation access before write admission.

Exact App grants are a separate approval gate. Begin permission review with Metadata read and Administration read for protection inspection; GitHub documents that bypass details are omitted without ruleset write access, so those candidate grants may be insufficient. Missing `bypass_actors` is **unknown**, never empty. Prove visibility with the App's actual installation token on a separately approved test target; do not use a human login's successful response as that proof. If Administration write is needed, surface the security trade-off and request explicit approval before adding it: such an inspector could change repository protections even if our code exposes only inspection operations. No write grant, App registration/installation or token mint is authorized by the architecture choice alone. Unproven/unavailable App inspection leaves useful enforced read-only access; do not widen grants, add a bypass, substitute personal credentials or lend inspector authority to agents. Broker write and native-read credential roles remain separate and unchanged.

Controlled trial evidence is now recorded in [the runbook](../../security/git-access-runbook.md): Metadata read + Administration read omitted both bypass fields and failed closed. Theo then explicitly approved Administration write **on the disposable trial only**; the same hash-pinned inspector obtained explicit empty bypass lists and passed. Production App grants/installations remain unapproved; this result must not be promoted to blanket settings/deletion authority. Enrollment now requires a pre-approved App/owner/repository-ID mapping in the same host registry and explicit project/ID arguments plus exact confirmation; it rechecks remotely after confirmation and saves atomically without overwriting a changed registry. No basename-derived authority or new App grants are created by enrollment.

At every admission/revalidation:

1. Fetch repository metadata and verify numeric ID, canonical name and current nonempty default branch. An empty repository needs human bootstrap before write admission.
2. Fetch all ruleset pages with parent rulesets included, then full details for the registry's two baseline IDs. Verify identity/source, active branch target, exact conditions, both history rules, PR rule and explicit empty bypass arrays. A name match alone never proves ownership. Unknown protection schema that prevents proving the floor fails closed.
3. Query active rules for the default branch and a deterministic, valid nested future feature name; require the baseline ruleset IDs in the returned rules. These checks corroborate effective enforcement, not a finite-sampling proof of all branches: exact `~ALL` without exclusions supplies that proof.
4. Read current default classic branch protection where supported and record existing rules/CI for migration comparison. A 404 here alone cannot prove absence: accept it only with independently verified baseline coverage. Failure to inspect a required baseline or enumerate its parents is never treated as absence. Existing classic/inherited rules may strengthen the floor; bypass in an unrelated ruleset cannot weaken the separate no-bypass floor.
5. Verify role-specific credential enrollment against the broker spec's minimal action grants: Contents write for mediated code/authorized merge; Issues/Pull requests write for required issue/comment/review/PR workflows; Metadata/Contents/Issues/Pull requests/Checks/Commit statuses/Actions read only where needed for reads. All real write credentials (including Project board writes) remain host-only. No Administration/Workflows/Checks/Statuses write or broader code reach is added to forwarding credentials. A separate genuinely read-only repo credential may support native `gh`; never downgrade a write token by client filtering. The current private-visibility check is not proof of exact grants. Where GitHub cannot expose PAT grants programmatically, require human-reviewed enrollment/replacement; legacy tokens are not grandfathered. Reject credential mismatch or expired enrollment. Inspector account-level authority is not evidence of a forwarding token's grants, nor the reverse.

Use pinned supported REST version (proposed `2026-03-10`, as current GitHub docs specify), JSON schema checks, complete pagination, bounded request and total deadlines, and no credential-bearing cross-host redirects. An API error is not an empty list. Never use stale success as fallback on a failed request.

Administrative remediation creates the two baselines without deleting/editing existing classic/ruleset protections, including the old `agents: protect default branch`. Adopt/update only registry-owned IDs with a reviewed before/after diff; preserve any stronger additions, reject conflicting duplicate names, and re-read/evaluate after writes. Never automatically remediate at launch. A failed partial installation stays read-only; do not roll back to weaker protections. Do not infer permission to merge PRs from a successful gate.

## Read-only fallback is an enforcement requirement

No successful check means **no agent write credential** and no local writes to the enrolled project. Read status/diff/log/source remains useful. A separately provisioned repo-scoped read-only credential can support private fetch/API inspection; never pass the write PAT and label it read-only. Without that credential, local reads and public remote reads remain available.

Clear inherited `GH_TOKEN`, `GITHUB_TOKEN`, enterprise equivalents, `GH_PROJECT_TOKEN`, credential-helper/askpass and Git config overrides; hide old stored GH credentials, SSH agent sockets/keys and credential-bearing logs/caches. Only afterward may the launcher supply an independently enrolled **read-only** repo token for native reads; inherited credentials or the old write PAT cannot qualify. Keep actual Project-board credentials host-only and mediate the necessary board operations with fixed typed templates. Ensure already persisted tokens from legacy sessions are addressed by server-side revocation. Preserve Cockpit's host desktop/phone/digest reads and human account review search without exposing host credentials to agents or expanding broker repository scope.

Mount the **whole enrolled checkout read-only**, plus actual gitdir/common dirs and linked metadata/config roots; pin roots against rename/replacement. Deny writes independently of inherited learned allow rules. Do not create missing hooks/config in a read-only repository: use a compatible Greywall mode/overlay. Withhold project Docker sockets, write-capable FigCraft automation and other host writer channels in read-only mode; merely unsetting `DOCKER_HOST` is insufficient if the socket remains mounted in the checkout. A sandbox cannot make a daemon perform writes that its own mount denies. Keep independent scratch space available; disposable scratch Git repositories are not a route to canonical credentials or canonical project writes.

**Blocking dependency:** `5b364923` is necessary metadata hardening, not evidence that this read-only contract exists. Greywall must provide and prove recursive, non-overridable read-only project/metadata mounts and socket masking with actual sandbox tests. If those cannot be composed today, implement/deploy that prerequisite before launching an unprotected checkout. Do not substitute a PATH shim, hooks, missing `GH_TOKEN`, `.git/config` protection or an ignored denyWrite entry. If safe read-only cannot be established, refuse that launch with a precise dependency error; do not silently start writable. This is the only fallback availability exception.

## Revalidation and honest limits

**Operational timings approved by Theo:** fresh admission per launch; scheduled inspector tick every **300 seconds (5 minutes)**; successful local-session evidence valid at most **600 seconds (10 minutes)** on a monotonic clock; total inspection deadline **30 seconds**. Every upstream write independently requires a fresh complete check, never a cached 600-second allowance. A failed or timed-out scheduled check triggers immediate containment/read-only relaunch, not a wait until hard expiry. The normal detection window for an otherwise idle writable local session is up to 300+30 seconds; the independent 600-second deadline must contain it if scheduling/checker progress fails. Suspend/resume and machine sleep invalidate evidence; wall-clock rollback cannot extend it. Never refresh a lease using stale/offline results. Timing approval is not approval of implementation, other resource limits or inspector credentials.

The companion broker spec quantifies the rate budget: a typical complete inspection costs 7 REST calls, scheduled checks coalesce per distinct repository (not per session), and every upstream write gets a fresh check. With the selected App, inspection requests consume the appropriate **installation** bucket, not the human user's PAT pool; multiple tokens/repositories in one installation share its quota. Broker/native/host read PATs of one user still share that user's pool. The approved schedule costs 84 inspector requests/hour/repo: 12 repos cost 1,008 scheduled-only. Token mint/refresh requests and additional merge/read/write traffic must be counted in their actual response-header buckets; no arbitrary-scale capacity is promised. Shared principal/resource accounting and measured headroom remain prerequisites. App installation/grants and other resources need approval before cutover; never stretch approved timings or use cached evidence/personal-login fallback to recover capacity.

Run the sandbox beneath a host supervisor that agents cannot signal/replace through a sandbox-visible control channel. On identity/protection failure, stop the entire sandbox process tree and publish the reason; restart the same conversation in a newly enforced read-only sandbox only after termination and channel isolation are confirmed. Do not pretend environment changes or a runtime JSON flag downgrade an already mounted writable sandbox. Supervisor death must stop its child sandbox (kernel parent-death/cgroup enforcement), not leave an orphan writer. PID/process-name matching is insufficient.

Track external writers separately. Existing Docker containers or automation jobs may outlive the sandbox and hold writable project binds. On migration or failure, quarantine that checkout until those channels are stopped/isolated through the appropriate host approval. Do not kill arbitrary containers or discard working trees automatically. A new read-only session must not regain those channels.

The selected broker checks each new write even inside valid 600-second local-session evidence; polling only bounds containment of already writable local sessions. It revokes its own session capability on failure without relying on GitHub PAT revocation. Already forwarded writes may complete, and a privileged administrator can change protections between verification and GitHub's receive transaction. Do not claim an atomic check-and-push guarantee or report a timed-out request as definitely uncommitted. Previously exposed PATs remain usable until GitHub revokes/expires them: removing a keyring entry, killing a process or rotating to a new token does not revoke the old token. Existing 90-day PAT lifetime is not a ten-minute security lease. Broker compromise or intentionally authorized human removal of protections remains outside the guarantee.
