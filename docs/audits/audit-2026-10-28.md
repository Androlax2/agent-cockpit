# Engineering workflow audit — 2026-10-28

## Executive summary

Cockpit has substantial behavioral tests, but this checkout has no tracked CI workflow,
workspace lint policy, or shared contributor/agent engineering handbook. Its two Rust
packages mix responsibilities that could support cheaper, more focused verification.
Adopt OpenKeychron's small Make-based gate and OpenLogi's scoped guidance and boundary
discipline. Refactor incrementally; copying their whole toolchain or crate layout would
introduce unnecessary machinery. This is a source inspection, not a passing baseline.

## Findings

### P2 — Tests are not a complete, reproducible engineering gate

- **Where:** `Makefile:20–26`, `apps/Cargo.toml:1–15`; tracked file inventory has no `.github/workflows/`.
- **What:** `make test` runs Python tests, builds OSD and runs release Rust tests. There
  are no format, Clippy, rustdoc or script-lint targets. Cargo commands lack `--locked`.
- **Why it matters:** review cannot rely on the same complete checks locally and on PRs.
- **Suggested fix (M):** shared Make targets called directly by Linux CI; preserve
  resource controls and the OSD prerequisite. Inventory GTK, terminal, Lua, fish, Node
  and browser prerequisites before asserting that an ordinary runner can execute all tests.

### P2 — Lint policy does not cover Cockpit's actual language mix

- **Where:** `apps/{cockpit,osd}/Cargo.toml`, `tools/`, `config/bin/.local/bin/`,
  `config/fish/`, `apps/cockpit/assets/remote/`, `config/codex/.codex/cockpit-bridge.mjs`.
- **What:** no tracked common lint configuration; extensionless Python and shell
  commands need coverage as well as named source files. Browser JavaScript is real source.
- **Suggested fix (M–L):** rustfmt/Clippy; Ruff; ShellCheck/shfmt; fish syntax/format
  checks; JavaScript linting; Markdown linting and local link checks. Use tracked paths
  plus shebang discovery, not extensions alone. Introduce strictness after measuring and
  fixing violations, with specific justified exceptions rather than blanket baselines.
- **Reference distinction:** Ruff, JavaScript and Markdown linting are Cockpit-specific
  recommendations, not claims about tools verified in the two reference CI files.

### P2 — AI and contributor guidance lacks a canonical engineering entry point

- **Where:** `CLAUDE.md:1–28`, `README.md`, `docs/superpowers/`,
  `config/bin/.local/bin/cockpit-agents/README.md`.
- **What:** project instructions primarily cover Git/apply/tests; architectural history
  is spread through feature plans and a long operational README. No tracked root
  `AGENTS.md`, development guide or project-specific skill index was found.
- **Suggested fix (M):** root agent map; scoped Rust, scripting, protocol/security and CI
  rules; development and architecture guides; small contributor checklist. Preserve
  `CLAUDE.md` authorization text and link/import canonical engineering instructions.
  Skills should teach verification and approved deployment, not duplicate policies or
  install a general-purpose skill collection. Coordinate README work with todo `a3fea48f`.

### P2 — Headless daemon logic carries a GTK package dependency

- **Where:** `apps/osd/src/registry.rs:1–24`, `apps/osd/src/lib.rs:4–7`,
  `apps/osd/Cargo.toml:6–13`.
- **What:** the registry explicitly has no GTK, but its owning package includes GTK.
- **Suggested fix (M):** first extract registry, chief and teams engine modules into
  `apps/crates/cockpit-daemon/`; keep GTK executable entry points in `apps/osd`.
  The engine initially depends on `cockpit`; this removes GTK, not all UI dependencies.
  Preserve daemon tests, including cross-layer tests using cockpit UI as a dev dependency.

### P2 — Shared contracts, storage and presentation need staged separation

- **Where:** `apps/cockpit/src/lib.rs:3–29`, `teams.rs`, `chief.rs`,
  `chief/store.rs`, `teams/store.rs`, `status.rs:121`, `costs.rs:534`, `todo.rs:604–645`.
- **What:** teams and chief contracts reference each other; their stores share SQLite
  ownership. Background modules call `app::refresh`, and todo persistence touches editor
  drafts. Splitting by filename would introduce cycles or change ownership semantics.
- **Suggested fix (L):** extract combined wire contracts into
  `apps/crates/cockpit-protocol/`, keeping authorization and storage with existing owners.
  Untangle refresh notification and draft persistence ownership before considering
  `apps/crates/cockpit-ui/`. Each new boundary needs a dependency regression check.

## Aligned and healthy

- Real executable/PTY tests in `apps/cockpit/tests/common/mod.rs` and protocol rejection
  cases in `apps/cockpit/tests/team_protocol.rs` are valuable refactoring protection.
- Daemon host operations already have a fakeable `System` boundary.
- Existing workspace, lockfile, Makefile and build wrapper are sufficient foundations.
- `apps/target/release` is used by installed wrappers and tests: keep workspace and
  binary locations stable while adding libraries under `apps/crates/`.
