# Cockpit architecture, engineering and autonomy review — 2026-10-30

## Executive summary

**Keep the five-crate design and finish its operational boundaries before moving the workspace.**
The refactoring delivered useful private modules, a UI-free core/daemon dependency graph,
shared checks and better engineering guidance. It did not establish a responsive event
loop, reliable end-to-end agent completion, or a verified release. The captured running
tree still has four crates; the core extraction is merged but absent from that tree.
Remote CI also contradicts a simple “all checks passed” delivery claim: PR #14 failed,
and PR #15 passed at its head while its merged-main run failed.

The next milestone should be **one exact-source, green, deployed and sustained-tested
baseline**. Reaching it requires reconciled CI/source and bounded runtime work; then
prioritize smaller incremental Chief context and evidence-backed agent completion.
A root `Cargo.toml` would improve navigation slightly but would fix none of the
demonstrated blocking, delivery or approval problems.

## Invariants used to judge the architecture

1. Agents cannot turn content, claimed identity or collaborator messages into host authority.
2. Durable state and its errors precede successful publication; uncertain delivery remains uncertain.
3. UI input and daemon control remain responsive during slow peers, stores and subprocesses.
4. Verification applies to an exact source and execution environment; merge, apply and live proof are distinct.
5. Work is bounded and attributed; restarts, retries and concurrent owners do not duplicate effects or erase evidence.

## Prioritized findings

### F1 — P1: Delivery lacks a single verified source-to-runtime chain

- **Where:** GitHub PRs [#14](https://github.com/Androlax2/agent-cockpit/pull/14) and
  [#15](https://github.com/Androlax2/agent-cockpit/pull/15); I/L `apps/Cargo.toml`;
  I `docs/ARCHITECTURE.md:25–49`; host receipts in the evidence appendix.
- **Observed:** #14 merged at `11:26:53Z`; its head check concluded failure at
  `11:31:37Z`. #15 head `bbfd0bc` passed, but merged main `4e616e8` failed.
  L contains the earlier four-crate graph and a live-only Chief coordination-wake change.
- **Impact:** “merged,” “locally green” and “applied” cannot safely stand in for each
  other. Integrating the newer tree without comparing live-only behavior risks regression.
- **Direction:** exact base/head/diff/build/process receipts; diagnose the current CI
  failure; reconcile live-only commits; verify the candidate and its actual installed
  binaries. Investigate required-check enforcement with its owner; do not assume a bypass
  from an empty ruleset listing.
- **Effort:** S–M, roughly 1–3 engineer-days plus approved delivery time. High confidence.

### F2 — P1: Recurring sidebar scheduling still performs synchronous host IPC

- **Where:** L `apps/cockpit/src/app.rs:2204–2245,2263,2375,8286–8288`,
  I `apps/cockpit/src/app.rs:1556–1597,2936–2938,2942–3025`,
  I/L `apps/cockpit/src/app/continuity_ui.rs:526–539`,
  `apps/cockpit/src/app/chief_ui.rs:13–15,52–68`,
  `apps/crates/cockpit-core/src/chief.rs:13–25`,
  `apps/crates/cockpit-core/src/teams/client.rs:242–265`; L `app.rs:8313–8317`.
- **Observed measurement:** 141 of 600 main-thread samples, **23.5%**, were in
  `unix_stream_read_generic`. Nine complete long sampled runs lasted approximately
  **6.003–8.005 seconds**, recurring roughly every **30.017–30.517 seconds**.
- **Already-collected incident evidence:** two complete traced cycles contain **111
  sequential host connections** and input-poll gaps of **7.825 s and 6.854 s**.
  The investigator classifies each cycle as one snapshot, 22 fresh-session reservation
  attempts and 88 existing-session reservation attempts. Counts, timing and copied-binary
  identity were independently checked; exact Rust line mapping remains attributed.
  Static source confirms snapshot collection followed by synchronous reservation loops.
  The architectural concern is accumulated scheduling IPC, not just one snapshot read.
- **Additional static path:** maintenance refreshes Chief synchronously before the bounded async
  team fetch. Chief snapshot collection permits three generations of up to 512 pages;
  each ordinary host request has per-I/O timeouts, without a whole-operation deadline
  on this snapshot path. This additional path is not established as the incident's cause.
- **Impact:** a slow daemon can still stop input processing. Moving App methods into
  files and fixing team polling alone do not enforce a responsive UI.
- **Direction:** the dedicated investigator owns the repair and live acceptance. Chief
  reports selecting a single-flight background scheduling worker; that is a reported
  direction, not delivery proof. Bound recurring work off the input loop and validate
  identity/generation before applying results, with sustained and slow-peer acceptance.
  Display deadlines/cache state must not become authority for dispatch: preserve
  authoritative reservation/admission checks before side effects.
- **Effort:** M, approximately 1–3 engineer-days after diagnosis. High confidence in the
  observed blocking category and inspected source paths; no fix/live acceptance receipt.
  The closed `68e5cb51` task resolved source access, not the freeze. Incident investigation
  remains with `ses_12729702f195758623a8976d`; it is not a prerequisite to finishing this audit.

### F3 — P1: The daemon's execution boundary is still the GLib event loop

- **Where:** I `apps/osd/src/bin/osd.rs:647–721,748–756`;
  `apps/crates/cockpit-daemon/src/registry.rs:3034–3152`.
- **Observed source:** queue ticks and pruning run synchronously in GLib callbacks;
  pane reconciliation scans sessions/panes and invokes tmux. Completed socket requests
  accumulate in `Vec<Received>` and one callback handles the whole drained batch.
- **Impact:** slow work can delay approvals, lifecycle transitions and unrelated clients.
  Reader-thread limits do not bound the completed queue, handler time or total work.
- **Direction:** bounded observation workers with immutable results; the existing registry
  owner applies results after identity/revision checks. Bound accepted work, dispatch
  slices and response writes; preserve explicit storage ownership. See S2/S3 in the roadmap.
- **Effort:** M–L, approximately 3–6 engineer-days across the existing pane and diagnostics
  owners. High source confidence; no live overload experiment performed.

### F4 — P1 release / Medium security: Response writes can block the control loop

- **Where:** I `apps/osd/src/bin/osd.rs:532–586,647–721` and
  `apps/crates/cockpit-daemon/src/fifo.rs:77–99`.
- **Source → sink:** a peer able to reach a team socket submits a bounded request;
  its reply stream reaches synchronous `write_all` in the GLib handler. The reader
  explicitly sets blocking mode on the shared socket; no write timeout is set in the
  inspected server path. A response exceeding available socket capacity
  can therefore hold that loop if the peer stops reading.
- **Impact:** local availability loss across control functions. This is a static risk,
  not proof of remote unauthenticated access or an observed attack.
- **Direction:** bounded response queues and whole-exchange deadlines outside GLib;
  preserve peer authentication and durable results. Test a small-buffer/non-reading
  client in isolation, then verify another client's control request still progresses.
  Serialization/write failures should produce bounded diagnostics, not empty default
  replies with ignored write errors.
- **Effort:** S–M, approximately 1–2 engineer-days within S3. High path confidence,
  medium confidence in practical triggering conditions until the fixture runs.

### F5 — P2: Incremental Chief delivery still repeats whole rosters and unbounded preparation

- **Where:** I `apps/crates/cockpit-core/src/chief/store.rs:2787–2815,4240–4251,4626–4640,5036–5047`.
- **Observed source:** a material availability change records the complete product-worker
  roster; incremental context republishes that roster. Snapshot recovery constructs and
  serializes all records before paging, including every unread completion.
- **Existing protection:** 50-record pages, 100 records per admitted turn, 60,000-byte
  context pages, frozen generations, durable `read_through`, and bounded unread retries.
  The Chief's own availability transitions are already excluded from manufacturing wakes.
- **Impact:** output bounds do not bound query/serialization work. Roster churn can use
  context on unchanged workers; blindly capping unread completions would lose work.
- **Direction:** entity/revision deltas, explicit tombstones, safe availability coalescing
  and a bounded snapshot-build cursor. Preserve a recovery snapshot and all unread
  decisions, completion/error records and authorization provenance.
- **Effort:** M–L, approximately 3–5 engineer-days with `153066df` and context owners.
  High source confidence; actual token savings are unmeasured.

### F6 — P1: Native receipt is not evidence of completed agent work

- **Where:** diagnostic receipts `bc043ad3697a`, `a2797eb17fca`; I Chief/Team delivery
  stores and `docs/chief-supervision.md`.
- **Observed:** native admissions completed in 17–49 ms in the sampled incident, while
  four requested turns failed with HTTP 429 and empty assistant content. The eventual
  ownership reply was created about **55.94 minutes** after the original clarification;
  that reply's admission took 88 ms.
- **Impact:** optimizing queue admission alone would miss the dominant stall. Repeated
  “received, please answer” wakes can spend context without producing a result.
- **Direction:** measure queued → admitted → execution outcome → verified task result
  separately. Preserve unknown/uncertain states; use quota-aware retry times, idempotency
  and one accountable owner. Completion claims require exact-source evidence, not the
  existence of an assistant turn or a closed todo.
- **Effort:** M, approximately 2–4 engineer-days coordinated with `5b91edcf` and quota
  owners. High confidence for this incident; population throughput remains unknown.

### F7 — P2: Approval friction often concerns evidence and environment, not needed authority

- **Where:** retained project approval results; I `AGENTS.md`, `.agents/skills/`,
  launch/verification entry points; source-access blocker `9b3d985d`.
- **Observed:** this review needed four approved host requests to acquire source, CI and
  runtime evidence. The retained mount has 34 completed result records, 10 nonzero;
  at least six concern failed clone Cargo/test commands. This is a convenience sample,
  not an approval failure-rate estimate.
- **Impact:** agents lose time rediscovering capabilities, source identity and check
  prerequisites. Host execution of agent-modified build files carries real authority;
  “just allow tests” is not a safe fix.
- **Direction:** project-scoped read-only evidence capabilities and reproducible sandbox
  verification first; typed brokers only where necessary. Bind grants to caller runtime,
  project, operation, resource bounds, expiry and revocation. Details in the autonomy appendix.
- **Effort:** M, staged pilot of roughly 3–5 engineer-days after approval. Medium confidence
  on avoidable volume; high confidence on the observed friction.

### F8 — P2: Core is headless, but public and platform boundaries remain broad

- **Where:** I `apps/crates/cockpit-core/src/lib.rs:3–31`, `remote.rs`, `paths.rs`,
  `approval.rs`, `teams/store.rs`; `apps/cockpit/src/app/`.
- **Observed:** core exports **29 public modules**, including stores, HTTP/phone support,
  subprocess-facing helpers and filesystem state. App children still operate on shared
  App state. Both are accurately documented; neither is a pure domain library.
- **Impact:** state/transport/presentation changes still cross several owners. A new
  crate per feature would add contracts and compatibility obligations without necessarily
  reducing this change amplification.
- **Direction:** inventory real consumers; keep orchestration private; name blocking
  boundaries and operation results. Narrow APIs incrementally, preserving existing
  compatibility exports. Extract another crate only for a demonstrated independent
  consumer, platform/dependency boundary or measured build benefit.
- **Effort:** M, approximately 2–4 engineer-days for one chosen boundary, not a global
  rewrite. High source confidence; build-speed benefit is unknown.

### F9 — P1 release: Packaging is staging, with at least one runtime dependency mismatch

- **Where:** P `packaging/arch/PKGBUILD:18–23`; I
  `apps/cockpit/src/approval/terminal.rs:168–197`;
  `docs/packaging/arch-package-staging.md:3–5,40–43,109–111`.
- **Observed source:** fish is optional in the package recipe, while the approval runner
  unconditionally constructs a fish command. Staging documentation explicitly leaves
  native source-free installation, startup, upgrade, uninstall and provenance unproved.
- **Impact:** a package can pass file-inventory checks yet fail a core approval workflow.
  A SHA in `release.json` establishes declared identity, not a source attestation.
- **Direction:** existing owner `1a7c54da` should reconcile required/optional capabilities
  and prove the native lifecycle on an isolated Arch system. Keep user grants and state
  outside package ownership. Integrity, provenance and activation need distinct evidence.
- **Effort:** S for classification; M–L, roughly 2–5 engineer-days for the release proof.
  High source confidence; native outcome remains unverified.

## Architecture recommendation and alternatives

The meaningful boundary is **who owns state, authority and blocking work**, not whether
libraries sit directly under `crates/`.

| Option | Scope and benefit | Cost and risk | Recommendation |
| --- | --- | --- | --- |
| **A — Stabilize the current five crates** | Keep `apps/` workspace; enforce nonblocking UI/control, bounded observation, durable delivery and explicit core APIs | Roughly 3–6 engineer-weeks for the full phased roadmap, overlapping existing work; first stabilization slices are smaller | **Choose now.** Smallest approach that addresses demonstrated failures |
| **B — A, then a root workspace with `crates/` and `apps/`** | Same runtime work plus a clearer top-level Rust entry point and dependency organization | Additional 2–4 engineer-days, perhaps a week with packaging/fixture consumers; target paths, manifests, scripts, CI and relative fixtures all move | Defer until a stable release and a concrete tooling/onboarding need justify it |
| **C — Dedicated headless daemon process and narrower platform/core packages** | Separate GTK presentation from the authoritative service process; strongest eventual lifecycle isolation | Roughly 3–6 additional engineer-weeks; new IPC, process supervision, activation and rollback contracts; greatest migration/security risk | Viable if measured faults persist across A's boundaries or a supported headless deployment needs it |

Estimates are planning judgments, not measured implementation duration. They exclude
approval wait and do not imply recruiting more workers or displacing current owners.

### Why these five crates exist

| Crate | Responsibility to retain | Boundary to strengthen |
| --- | --- | --- |
| `cockpit-protocol` | Wire contracts, validation and identity shapes | No authority, SQLite, UI or executable policy; additive/versioned evolution |
| `cockpit-core` | Shared client/state operations, persistence, reusable summaries | Headless, not “pure”; explicit blocking/I/O and error ownership; smaller consumer-facing surface |
| `cockpit-daemon` | Registry and collaboration orchestration, host-operation decisions | Sole authoritative state application; bounded workers return observations, never grants |
| `cockpit` | CLI/terminal binaries, UI state and terminal adapters | Rendering/input use projections; binary ownership and compatibility imports stay explicit |
| `osd` | GTK entry points and presentation integration | Short callbacks; authoritative work must not wait on presentation or a socket writer |

Production graph isolation is real: core and daemon exclude the terminal package and
GTK/Ratatui/Crossterm; protocol also excludes SQLite. OSD still depends on `cockpit`,
and daemon dev-only tests deliberately do too. Neither fact disproves the narrower
production-core claim. All 294 external lockfile package records match I versus L;
this is dependency stability, not a fresh vulnerability scan.

Do not split Team and Chief databases: their shared transaction, migration and error
ownership is a useful invariant. Do not add a service/repository facade or a UI crate
merely to rename application glue. A future `cockpit-platform` or standalone daemon
requires measured consumers and approved scope, not a diagram alone.

## Engineering enforcement to keep and finish

**Keep:** Make as canonical entry point; locked Cargo commands; exact tool/action pins;
Python/shebang language discovery; Rustdoc/Clippy; dependency/license checks; fake host
operations; real CLI/PTY tests; five graph/normal-feature guards; default-off fixture support;
resource admission and the shared full-suite lock.

**Finish:** Linux shell-dialect parity; concurrent launcher fixture/root-cause repair;
exact merge-source checks; named not-run outcomes after fail-fast; consumer-aware test
selection; version-skew and transport-fault tests; sustained responsiveness; source-to-binary
release evidence. Retrying a broad suite until green is not a fix for shared-state races.

The repository already has scoped agent rules and two workflow skills. Their initial
four-scenario evaluation found no measured advantage over ordinary guidance. The global
instruction file alone measured 28,294 bytes, roughly 7,074 tokens by the crude bytes/4
heuristic. Improve command discovery, receipts and scoped loading before adding more prose.
Any instruction reduction must preserve actual approval/security policy and needs its
owner's approval; token estimates are not provider billing measurements.

## Immediate decision

Approve **Option A's stabilization direction** and the phase-0/1 acceptance criteria in
the roadmap. Keep the urgent freeze investigator and existing runtime/package owners.
Reconsider workspace relocation only after the exact-source release and responsiveness
gates pass. The report proposes work; it does not authorize implementation or host changes.
